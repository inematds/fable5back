1.1~30 min

📰 Fable 5: context and window of opportunity

What happened from launch to the global return, and why this is the right time to learn how to prompt this model.

What it is:

Fable 5 and Mythos 5 launched on Jun 9, 2026; U.S. government export controls on Jun 12 led Anthropic to suspend access for everyone; global access returned on Jul 1, 2026.

Why learn:

Understanding the context helps you avoid thinking the model “disappeared” because it was too dangerous — and helps set realistic expectations.

Key concepts:

Claude Fable 5; Claude Mythos 5; export controls; Project Glasswing.

What it is:

Amazon researchers reported a way to bypass Fable 5’s safeguards. But Anthropic’s own test showed that much less capable models—Opus 4.8, GPT-5.5, Kimi K2.7, even Haiku 4.5 and Sonnet 4.6—generated the SAME exploit demonstration.

Why learn:

Context over drama—the suspension was a regulatory precaution, not a failure unique to Fable 5.

Key concepts:

Software vulnerability; comparative test between models; regulatory precaution.

What it is:

Fable 5 is included in up to 50% of the weekly usage limit through 7/jul/2026 for Pro/Max/Team/some Enterprise plans; after that, via usage credits.

Why learn:

Knowing the limit helps avoid cost or quota surprises in the first week of use.

Key concepts:

Weekly usage limit; usage credits; Claude Platform, Claude.ai, Claude Code, Claude Cowork.

What it is:

Same capabilities as Fable 5, but without the safety classifiers — restricted use only through Project Glasswing, for defensive cybersecurity.

Why learn:

Keeps you from confusing the two models and their very different use cases.

Key concepts:

Project Glasswing; safety classifiers; defensive cybersecurity.

What it is:

Fable 5's global rollout is the right time to learn how to prompt a model that behaves differently from Opus 4.8.

Why learn:

Anyone who learns the right techniques from the start avoids months of trial and error.

Key concepts:

Adoption window; learning curve; changes to prompting habits.

What it is:

Dan Shipper (Every) gave Fable 5 a 91/100 on the internal “Senior Engineer” benchmark, compared with 63 for Opus 4.8. Boris Cherny (Anthropic) publicly called it “the best model I’ve ever used for code, by a wide margin.”

Why learn:

Signals the size of the capability jump—even though it’s a third-party account, not an official Anthropic fact.

Key concepts:

“Senior Engineer” benchmark; early adopter account; “warp drive for coding.”

🎯 Give the reason + don't ask for reasoning

Intent context at the start, and the official refusal trigger that appears when you ask the model to show its reasoning.

What it is:

Intent context—saying WHAT the thing you’re asking for is FOR, not just WHAT to do.

Why learn:

It’s established prompt engineering practice (the video already makes this case)—it helps the model make the right micro-decisions on its own.

Key concepts:

Task intent; purpose context; general practice, not a verbatim official quote from the Fable 5 doc.

What it is:

Asking Claude to reproduce its internal reasoning in the response may trigger the reasoning_extraction refusal category, specific to Fable 5.

Why learn:

Old skills and system prompts that ask you to "show your reasoning" now trigger refusals and fallback to Opus 4.8.

Key concepts:

stop_reason: "refusal"; reasoning_extraction; adaptive thinking.

What it is:

The official documentation recommends auditing older skills for “echo/transcribe/explain” instructions about internal reasoning.

Why learn:

Migrating from Opus to Fable 5 without this audit increases refusals for no apparent reason to anyone who doesn’t know the trigger.

Key concepts:

Harness instructions; structured thinking blocks; system prompt audit.

What it is:

If the application needs visibility into reasoning, the right approach is to read the structured "adaptive thinking" blocks — not to request it in the response text.

Why learn:

Meets the need for transparency without triggering a reasoning_extraction refusal.

Key concepts:

Adaptive thinking; structured blocks; reasoning visibility.

What it is:

Examples of how to tie the “why” to a technical prompt—for example, “I’m reviewing this for production” vs. “It’s just a draft.”

Why learn:

The same technical request leads to very different behavior depending on the stated reason.

Key concepts:

Task prompt; context signaling; conditional behavior.

What it is:

Older instructions asking it to "explain your step-by-step process" were normal with Opus and break in Fable 5.

Why learn:

Finding this pattern helps avoid a silent fallback to Opus 4.8 and unexplained extra costs.

Key concepts:

Legacy skills; silent fallback; prompt review.

🛑 Negative prompting + boundaries

The official anti-tidying prompt and when the right deliverable is just an assessment, without applying any changes.

What it is:

Explicitly say what the model must NOT do, not just what it should do.

Why learn:

At high effort, Fable 5 may gather context and deliberate beyond what the task requires — negative prompting keeps this in check.

Key concepts:

Negative prompting; over-engineering; overplanning.

What it is:

The official text says not to add features/refactors/abstractions beyond the scope, not to clean up code around a bug fix, and not to create a helper for a one-off operation.

Why learn:

It’s the most direct official quote against unrequested "tidying."

Key concepts:

Anti-tidying; premature abstraction; validation only at system boundaries.

What it is:

The same official prompt covers not designing for hypothetical future requirements — just doing the simplest thing that works well.

Why learn:

Fable 5 tends to be more thorough by default; constraining it saves tokens and review time.

Key concepts:

Deliberate simplicity; feature flags; backward-compatibility shims.

What it is:

When the user is describing a problem or thinking aloud, the deliverable is the assessment—report and stop, don't apply a fix without asking.

Why learn:

Keeps you from changing system state (restart, delete, config) without evidence that truly supports the action.

Key concepts:

Deliverable = assessment; destructive/irreversible action; confirmation before acting.

What it is:

The negative prompting block works well pasted into CLAUDE.md, the system prompt, or the beginning of a session.

Why learn:

Pasting it once addresses the tendency to "tidy up" in every subsequent task in that project.

Key concepts:

CLAUDE.md; system prompt; session/project scope.

What it is:

After pasting the prompt, observe whether bug fix tasks start coming through without extra refactoring in subsequent sessions.

Why learn:

Closes the loop of “I tested and confirmed,” not just “I think it helped.”

Key concepts:

Empirical verification; before-and-after comparison; scope of the delivered change.

1.4~45 min

🏁 Let it act + prove it's finished

Anti-overplanning at the start and evidence verification at the end—the two official prompts that most change agentic behavior.

What it is:

The official prompt says to pause for the user only when the task truly requires it—a destructive or irreversible action, a real change in scope, or input only they can provide.

Why learn:

Eliminates the habit of “asking too many questions” that stalls the autonomous loop on tasks that already had enough information.

Key concepts:

Anti-overplanning; irreversible action; end of turn.

What it is:

If one of the cases that requires the user comes up, the right thing is to ask and end the turn there — never end by "promising" to do it later.

Why learn:

Eliminates “early stopping” without action — rare, but reported in long sessions.

Key concepts:

End of turn; promise vs. action; rare early stopping.

What it is:

Before reporting progress, audit every claim against a tool result from this session; report only what you can point to evidence for.

Why learn:

In Anthropic’s test, this nearly eliminated reports of fabricated status updates, even in tasks designed to induce them.

Key concepts:

Evidence from tool results; accurate reporting; no hedging.

What it is:

If a test fails, report the output; if a step was skipped, say so; when something is ready and verified, state it plainly.

Why learn:

It’s the opposite of the "pretty status report" the prompt is trying to eliminate.

Key concepts:

Reported failure with output; skipped step; claim without hedging.

What it is:

For long tasks, a verifier subagent with fresh context checks the work against the specification at defined intervals.

Why learn:

Fresh-context verifiers tend to outperform self-criticism by the same agent that did the work.

Key concepts:

Fresh-context verifier; check interval; specification as the reference.

What it is:

Compare progress reports before and after pasting both prompts (act + prove) into multi-step tasks.

Why learn:

Closes the practical loop — pasting the prompt isn’t enough; you have to confirm the actual behavior change.

Key concepts:

Before-and-after comparison; multi-step task; behavior confirmation.

1.5~35 min

✂️ Say less, not more

Instruction-following has improved enough for you to guide it with one sentence—and how to structure the final response without turning it into a telegram.

What it is:

Fable 5 follows instructions well enough that you can guide its behavior with a short sentence instead of listing every rule by name.

Why learn:

Prompts and giant system prompts become dead weight—the model already understands the intent with far less text.

Key concepts:

Instruction-following; brief instruction; unnecessary enumeration.

What it is:

The first sentence of the response should answer “what happened” or “what did you find”—the TLDR the user would ask for; details and reasoning come afterward.

Why learn:

It’s the most direct official quote on how to structure the final response for the reader.

Key concepts:

Outcome-first; TLDR; supporting detail after the result.

What it is:

The official prompt says to distinguish readability from concision: cut details that don’t change the reader’s next action, rather than compressing the writing into fragments or abbreviations.

Why learn:

Saving tokens by turning text into a telegram makes it harder to read; saving by selecting content does not.

Key concepts:

Readability; content selection; text fragmentation.

What it is:

After working for a long time without the user watching, the final summary should be a re-grounding — lead with the result and explain each identifier (file, commit, flag) as if it were new.

Why learn:

It’s the official prompt that keeps the user from getting lost when returning from a long, autonomous session.

Key concepts:

Re-grounding; shorthand between tool calls; clarity over brevity.

What it is:

Thinking aloud in brief between tool calls is normal—unlike the final summary, which needs to be complete for a reader who didn’t see any of that.

Why learn:

Keeps you from thinking that “being telegraphic all the time” is the right behavior for every interaction.

Key concepts:

Intermediate thinking; final summary; reader audience.

What it is:

Test the same request with and without the "say less" prompt and compare whether the answer became more direct without turning into an incomprehensible fragment.

Why learn:

Closes the loop — “say less” doesn’t mean “be less clear.”

Key concepts:

Clarity over brevity; response comparison; personal calibration.

⚙️ Effort and safety routing

The 5 official effort levels and how Fable 5 truly refuses—4 categories, billing, and fallback to Opus 4.8.

What it is:

max, xhigh, high (default), medium, and low—each with an official use case, from “deeper reasoning” to “simple tasks, e.g., subagents.”

Why learn:

Choosing the right level saves tokens without sacrificing quality where it isn’t needed.

Key concepts:

output_config.effort; max/xhigh/high/medium/low; behavior vs. token budget.

What it is:

Official quote: at lower effort levels, Claude still thinks through sufficiently difficult problems, but thinks less than it would at a higher level for the same problem.

Why learn:

Debunks the myth that low effort always means weak responses.

Key concepts:

Behavioral signal; token budget; sufficiently difficult problem.

What it is:

The docs’ practical recommendation: low levels in Fable 5 still perform well—don’t assume “low effort = weak” just because that was true when switching from Opus.

Why learn:

Keeps you from setting “high”/“max” on everything out of old habit and needlessly doubling the cost.

Key concepts:

Habit migration; cost vs. performance; subagents running on low.

What it is:

This isn’t “routing” with a product name—it’s an HTTP 200 with stop_reason: "refusal" and a category in stop_details.category.

Why learn:

Treating it as a generic error (blind retry) is the wrong approach; treating it as a valid response with metadata is the right one.

Key concepts:

HTTP 200; stop_reason; stop_details.category.

What it is:

cyber, bio, frontier_llm, and reasoning_extraction — each with the official text describing what triggers that category.

Why learn:

Knowing the category guides the right prompt adjustment — e.g., reasoning_extraction is resolved by removing "show your reasoning."

Key concepts:

cyber; bio; frontier_llm; reasoning_extraction.

What it is:

A refusal before any output is not charged; a refusal mid-stream charges for the input and output already emitted. There are 3 ways to fall back to Opus 4.8: server-side, SDK middleware (BetaRefusalFallbackMiddleware), or a manual retry with "fallback credit".

Why learn:

Deciding on a fallback strategy prevents product disruption when a refusal occurs in production.

Key concepts:

Refusal billing; BetaRefusalFallbackMiddleware; fallback credit.

🧩 Bonus: subagents, memory, and send_to_user

Extra tricks found only in the official documentation, not in the original video — delegation, persistent memory, and partial updates.

What it is:

Fable 5 dispatches parallel subagents more readily than previous models; the official prompt recommends delegating independent subtasks and continuing to work while they run.

Why learn:

Asynchronous communication between the orchestrator and subagent replaces "blocking waits" with true parallelism.

Key concepts:

Parallel subagents; asynchronous communication; intervention if a subagent goes off track.

What it is:

Subagents that maintain context across subtasks save time and cost through cache reads.

Why learn:

Reusing context across subtasks is cheaper than recreating everything from scratch with each call.

Key concepts:

Long-lived subagent; cache reads; cost per subtask.

What it is:

The official prompt recommends saving one lesson per file, with a one-line summary at the top, recording confirmed corrections and successes—and why they mattered.

Why learn:

Disorganized memory becomes noise; 1 lesson per file keeps everything searchable and updatable.

Key concepts:

1 lesson per file; update an existing note; delete a note that turns out to be wrong.

What it is:

The official bootstrap prompt asks you to reflect on previous sessions, use subagents to identify key themes and lessons, and save them to a specific destination that can be referenced in the future.

Why learn:

Start the memory system with a real signal instead of an empty note.

Key concepts:

Bootstrap; identification subagents; future reference to the memory destination.

What it is:

Gives the agent a tool whose input is shown to the user exactly as written, without ending the turn — useful for a partial deliverable, a progress update with specific numbers, or answering a question asked mid-loop.

Why learn:

For long-running/asynchronous agents, solves the problem of “the user gets no updates until the end.”

Key concepts:

Input displayed verbatim; no end of turn; partial progress update.

What it is:

Skills built for earlier models are often too prescriptive and degrade Fable 5's quality; the recommendation is to review them and consider removing old instructions if the default performance is already better.

Why learn:

Closes the course loop — migrating isn’t just about learning a new technique; it’s also about getting the old prompt out of the way.

Key concepts:

Overly prescriptive; default performance; skill review.
