2.1~35 min

🎯 Choose the right task + explain why

A model of this caliber is wasted on trivial tasks — and gives much better answers when it understands the real reason behind the request.

What it is:

An advanced model like Fable 5 is wasted on summarizing text or answering quick questions — its real value shows up in difficult problems: reviewing an entire project's architecture, assessing product/technology/business risks, turning an idea into an execution plan, analyzing a long document, and reviewing code/security/UX/databases.

Why learn:

Directing the right tool to the right task is the first filter for using the model as a work agent, not as an expensive chat.

Key concepts:

High-value task; wasted capacity; diagnosis vs. quick question.

What it is:

A prompt template that asks for a diagnosis of the core problem, strategic decisions, risks, a step-by-step execution plan, concrete deliverables, and what to do now — in order.

Why learn:

It’s a ready-to-copy-and-adapt prompt, tested on real project analysis tasks.

Key concepts:

Prompt tested in practice (not an official quote); senior agent; deliverable in stages.

What it is:

The model responds better when it understands the intent behind the request: the larger goal, audience, context, and expected result — not just the bare instruction.

Why learn:

"Create an AI learning path" is weak; saying who it’s for, what its goal is, and what final outcome you expect completely changes the quality of the response.

Key concepts:

Intent context; target audience; stated expected outcome.

What it is:

A template that states the objective ("professionals who want to apply AI at work by practicing every day") before asking for a learning path with an initial assessment, daily practice, a weekly project, support, progress criteria, and a final outcome.

Why learn:

Comparing the weak and strong prompts side by side clearly shows the benefit of adding context before asking.

Key concepts:

Weak vs. strong prompt; structure with progress criteria; expected final result.

What it is:

In practice: before writing any heavy analysis prompt, first confirm that the task warrants the model (Tip 1), then establish the real reason for the request (Tip 2)—together, they make a complete diagnostic prompt.

Why learn:

Used separately, each tip helps a little; combined, they change the kind of response you get.

Key concepts:

Task filter + intent context; complete diagnostic prompt.

What it is:

Common mistakes: using the model for a summary/caption task; asking for analysis without saying who it’s for or what outcome you expect; copying a generic prompt without adapting it to the actual project.

Why learn:

Quick checklist before starting: is the task difficult enough? Is the rationale explicit? Are the audience and outcome clear?

Key concepts:

Pre-prompt checklist; adaptation to the real project; explicit rationale.

🎚️ Control the depth + set limits

Not every task needs maximum reasoning—and before letting the agent act, you need to make clear what it can and cannot do.

What it is:

Low: summary, caption, text edit, quick idea. Medium: simple planning, comparison, content review. High: strategy, architecture, audit, product decision. Maximum: critical issue, migration, security, complex risk analysis.

Why learn:

Asking for maximum reasoning on a trivial task costs more and takes longer without any benefit—and the opposite produces an answer that’s too shallow for a serious decision.

Key concepts:

Depth of analysis; cost × complexity; calibration by task type.

What it is:

A short prompt that limits where to apply depth: "use deep analysis only for the strategic part. Don't overcomplicate the solution. Don't create unnecessary abstractions. Deliver the simplest solution that solves the problem well."

Why learn:

Focuses the expensive effort where it matters and keeps the rest of the response from becoming unnecessarily complex.

Key concepts:

Selective depth; simplest solution; avoid over-abstraction.

Technical/API equivalent: module 1.6 from Track 1 covers the official effort levels (low/medium/high/xhigh/max).

What it is:

Strong models may take too much initiative — before technical analysis or execution, you need to make clear what the agent can and can’t do on its own.

Why learn:

Without a declared limit, “evaluate this server” can turn into “I restarted the service”—an expensive surprise in production.

Key concepts:

Explicit limits; agent initiative; separation of evaluation and execution.

What it is:

"First, just assess. Don’t change files, restart services, create a branch, edit configuration, or run destructive commands. Provide a diagnosis with evidence. Then say exactly what changes you recommend and why."

Why learn:

Separate it into two explicit steps—evaluate, then recommend—before any real action takes place.

Key concepts:

Evaluation without action; evidence-based diagnosis; recommendation separate from execution.

This echoes the boundary technique from Learning Path 1, module 1.3, which is backed by Anthropic’s official documentation.

What it is:

For a real security audit: request high reasoning depth only for the risk analysis (tip 3), but lock execution with “evaluate only, don’t change anything” (tip 4)—the agent thinks deeply and still won’t touch production without permission.

Why learn:

Unlimited depth is a risk; limits without depth lead to shallow analysis — both tips complement each other.

Key concepts:

Depth kept in check by limits; safe auditing; think deeply without acting on your own.

What it is:

Common mistakes: asking for maximum depth on every task out of habit; saying “evaluate the system” without specifying what it must not touch; confusing evaluation with authorization to execute.

Why learn:

Quick checklist: does the requested depth match the actual complexity? Are action limits explicit before any technical analysis?

Key concepts:

Pre-prompt checklist; habit of maximum depth; explicit limit before analysis.

🔍 Real verification + specialized subagents

Never accept “done” without evidence—and replace the single opinion with a structure of subagents that analyze the problem through different lenses.

What it is:

Never accept “done” without evidence—in code, automation, databases, deployments or documents, the model needs to prove what it did.

Why learn:

Without requiring proof, it’s easy to get a polished status report that doesn’t match what actually happened.

Key concepts:

Real evidence; test run; verifiable log/output.

What it is:

"Before saying something is done, confirm it with real evidence: a test run, changed file, log, command output, or verifiable result. If it wasn’t verified, clearly say: 'not verified.' If it failed, show the failure. If you skipped a step, say so."

Why learn:

Turns "I trust the answer" into "I check the evidence"—it works in any domain, not just code.

Key concepts:

Explicitly say "not verified"; show the failure instead of hiding it; state when a step was skipped.

This echoes the completion proof technique from Learning Path 1, module 1.4, which is backed by Anthropic’s official documentation (it nearly eliminated reports of fabricated status in the internal test).

What it is:

Instead of a single answer, analyze the same problem through several specialized lenses — strategy, product, communications, technology, and a skeptic who looks for flaws.

Why learn:

Good for evaluating ideas, offers, products, projects, and campaigns—the final synthesis is more robust than a one-shot analysis.

Key concepts:

Role structure; skeptical agent; consolidation with priorities.

What it is:

"Use a subagent structure: Agent 1 analyzes strategy and positioning. Agent 2 analyzes the product and user journey. Agent 3 analyzes content and communication. Agent 4 analyzes technology and automation. Agent 5 acts as a skeptic and looks for flaws. Then consolidate everything into a single recommendation, with priorities."

Why learn:

It’s a ready-to-use template for evaluating any complex decision across multiple dimensions at once.

Key concepts:

5 fixed roles; one consolidated recommendation; explicit priority.

Cross-reference with subagent delegation from the Learning Path 1, module 1.7: that one is about HOW to delegate technically; this one is about WHICH role structure to use.

What it is:

In practice, Agent 5 (the skeptic) in the subagent structure is the mechanism for real verification applied to decisions—it exists to reject an easy “done” and demand evidence before the final recommendation.

Why learn:

Verification isn't just for code—the skeptic role among subagents applies the same principle to product and strategy decisions.

Key concepts:

Skeptical as a verifier; evidence before recommendations; a dedicated role for challenging assumptions.

What it is:

Common mistakes: accepting “done” without asking for evidence; using only 1 perspective for a complex decision; skipping the skeptical agent because you think it will slow things down.

Why learn:

Quick checklist: is there concrete evidence for “done”? Was the decision reviewed from more than one perspective? Did the skeptic have a voice in the final synthesis?

Key concepts:

Pre-acceptance checklist; multiple perspectives; skeptic’s voice in the synthesis.

🗂️ Project memory + keep going until complete

The strongest use isn’t the perfect prompt; it’s continuous project memory—and knowing when the agent should execute instead of stopping early.

What it is:

The strongest use of Fable 5 isn’t getting the perfect prompt right once—it’s continuous project memory: positioning, target audience, offers, voice, mistakes to avoid, confirmed decisions, validated prompts, each in its own file.

Why learn:

Without memory, every session starts from scratch and repeats the same mistakes that were already fixed.

Key concepts:

Project memory; topic-based folder structure; confirmed decision vs. hypothesis.

What it is:

"Whenever we learn something important about this project, record it in memory. Format: decision or lesson; why it matters; where to apply it; what to avoid; date. Don’t duplicate information. Update the existing note when needed."

Why learn:

Turns memory into an automatic session habit, not a manual task that gets forgotten.

Key concepts:

Structured record with a date; anti-duplication; update of an existing note.

Cross-reference it with the official memory system for Learning Path 1, module 1.7 ("1 lesson per file"), which is officially supported by Anthropic's documentation.

What it is:

For long tasks, the model may stop too early or end with a promise instead of executing — make it explicit that it should continue once it has what it needs.

Why learn:

Useful for code, documentation, planning, and content creation—any long task where stopping halfway means rework.

Key concepts:

Execution instead of promises; stop only when necessary; destructive actions as an exception.

What it is:

"If you already have enough information, proceed. Don’t end with a promise, plan, or generic question. Stop only if you need information that only I can provide or if the action is destructive or irreversible."

Why learn:

Closes the “I’ll do it later” loop that unnecessarily stalls long sessions.

Key concepts:

Explicit stopping criterion; irreversible action as the only exception; end of “empty promises.”

Cross-reference with the anti-overplanning from the Learning Path 1, module 1.4, which is backed by Anthropic’s official documentation.

What it is:

Project memory is precisely the “enough information” that frees the agent to execute without pausing—the more complete the memory, the less legitimate reason the agent has to stop early.

Why learn:

The two tips form a cycle: well-maintained memory reduces unnecessary interruptions, and each run generates a new lesson for memory.

Key concepts:

Memory as fuel for execution; the memory-action-lesson cycle.

What it is:

Common mistakes: never recording lessons in memory; letting the agent stop out of habit from asking for confirmation; duplicating a note instead of updating the existing one.

Why learn:

Quick checklist: was this session’s lesson recorded? Did the agent execute or just promise? Is memory free of duplicates?

Key concepts:

Session closeout checklist; recording vs. forgetting; duplicate note.

🖼️ Vision for interfaces + defensive security

Use the model's vision to review real screens — and request a defensive security review instead of an exploit, without triggering a refusal.

What it is:

Assess the clarity, conversion, and impact of screens, pages, PDFs, and visual assets by sharing a screenshot or image—instead of just asking “make it look better.”

Why learn:

A structured visual review points out a specific, actionable problem instead of offering a vague aesthetic opinion.

Key concepts:

Structured visual review; first impression; generating questions vs. desire.

What it is:

"Analyze this screenshot or image. Compare it with the goal: helping someone quickly understand the value of the offering. Tell me: where the eye stops first; what’s confusing; what creates desire; what raises questions; what to cut; what to change to increase conversion."

Why learn:

Each question prompts a concrete, testable answer instead of a generic “it’s good.”

Key concepts:

6 visual review questions; cuts vs. additions; conversion as a criterion.

What it is:

In security, asking for a defensive review instead of exploration or attack avoids a blocked response and keeps the focus on protection.

Why learn:

How you frame the question determines whether you get real help or a refusal — even when asking about the same vulnerability.

Key concepts:

Defensive framing; avoidable refusal; focus on protection.

What it is:

"Review my server code defensively. Look for bugs, missing validation, authorization issues, accidental data exposure, configuration failures, and operational risks. Don’t create an exploit. Don’t show attack steps. Just identify the risk, affected file, likely cause, and defensive fix."

Why learn:

It’s literally the practical strategy for avoiding a "cyber" category refusal during a legitimate security review.

Key concepts:

No exploit; risk + cause + fix; refusal avoided through framing.

Cross-reference with the refusal category cyber explained in the Learning Path 1, module 1.6, which is backed by Anthropic’s official documentation—this tip is the practical strategy to avoid triggering that behavior.

What it is:

For a product launch: use the visual review (tip 9) on the landing page/screenshot before publishing, and the defensive review (tip 10) on the backend that supports the form—cover the feature’s experience and security.

Why learn:

Together, the two tips cover “what the user sees” and “what protects what they don’t see”—security is never just code, and UX is never just aesthetics.

Key concepts:

Experience review + risk review; full coverage of a feature.

What it is:

Common mistakes: asking to “make it look nicer” without a conversion criterion; framing a security review as an exploit/attack request; reviewing only the screen and forgetting the backend.

Why learn:

Quick checklist: are all 6 visual review questions answered? Is the security review framed as defensive? Did it cover both screen and server?

Key concepts:

Pre-publication checklist; correct framing; screen + server coverage.

🔁 Loops with verification + external memory

A good loop needs focus, judgment, testing, and learning — and long-running work can't depend only on the chat history.

What it is:

"Review my app every day" is a weak loop — a good loop needs focus (a small area), criteria (based on memory), testing, and a recorded lesson from each cycle.

Why learn:

Repetition without criteria wastes budget and doesn't measurably improve anything; a loop with verification actually improves, cycle by cycle.

Key concepts:

Weak vs. strong loops; focus per cycle; criterion saved in memory.

What it is:

"Each cycle: 1) choose a small area of the system; 2) analyze it based on the criteria already saved in memory; 3) propose an improvement; 4) implement it only if it’s safe and reversible; 5) run a test; 6) ask the verifier to try to find an error; 7) record what you learned."

Why learn:

Each step in the loop has a specific purpose—skipping one (usually step 6 or 7) is the most common reason a loop fails to make progress.

Key concepts:

7 steps of the loop; safe, reversible change; dedicated verifier.

Cross-reference with subagent verification from the Learning Path 1, module 1.4, which is backed by Anthropic’s official documentation (“establish a method for checking your own work”).

What it is:

Don’t rely only on chat history—create a file, database or supporting documentation that survives the end of the session.

Why learn:

Chat history disappears or gets too long to be useful; external memory is what makes weeks of work possible, not just a single session.

Key concepts:

External memory; persistence beyond the session; supporting documentation.

What it is:

Target audience, communication tone, offers, campaigns that worked, technical rules, strategic decisions, recurring mistakes, work processes, validated prompts, quality standards.

Why learn:

It’s the reference list for deciding what’s worth recording—it prevents empty memories or memories with too much noise.

Key concepts:

External memory categories; recorded quality standard; documented recurring error.

What it is:

Step 7 of the loop (“record the lesson learned”) is exactly where the loop feeds external memory — without external memory, the loop relearns the same thing every cycle.

Why learn:

The two tips close a virtuous cycle: the loop generates a lesson, external memory stores it, and the next cycle starts with a stronger criterion.

Key concepts:

Virtuous loop-memory cycle; criteria that grow with each cycle.

What it is:

Common mistakes: running a loop without a defined focus (“review everything”); skipping the verifier step; relying only on chat for work that lasts weeks.

Why learn:

Quick checklist: does the cycle have a small focus and a saved criterion? Did the verifier run? Was the lesson added to external memory, not just the chat?

Key concepts:

Cycle checklist; small focus; lesson outside the chat.

Recap of the 12 tips in a cheat sheet, the complete master prompt to copy, and a map of how the course’s two tracks connect.

What it is:

The 12 tips in brief: the right task, explicit reason, calibrated depth, limits before acting, real verification, specialized subagents, project memory, continue until done, interface awareness, defensive review, verification loop, external memory.

Why learn:

Serves as a quick reference to review before writing any new work prompt.

Key concepts:

Cheat sheet of the 12 tips; quick pre-prompt reference.

What it is:

The complete generic prompt combines context, objective, working mode (subagents, evidence before making claims, execution instead of promises, project memory), and task—ready to paste at the start of any new project.

Why learn:

It’s the module’s largest code box—the condensed version of everything the track taught, ready to copy and adapt.

Key concepts:

Master prompt; declared work mode; first next step.

What it is:

Always replace: the context paragraph and the final task with details specific to your project. Always keep: the 7 items in the work mode—they’re what make the prompt work as an agent, not as a chat.

Why learn:

Keeps you from rewriting the prompt from scratch for every project—only the project-specific part changes.

Key concepts:

Variable part vs. fixed part; reuse across projects.

What it is:

"Fable 5’s value isn’t in giving better answers. It’s in working better. The weak way to use it is to ask for answers. The strong way is to build a system with context, memory, subagents, verification, and continuous execution. Those who use the model only as a chat tool will get better answers. Those who use it as a work system will gain a real advantage."

Why learn:

It’s the central thesis of track 2—all 12 previous tips are meant to move out of the chat and into the work system.

Key concepts:

Chat vs. work system; real advantage; continuous execution.
