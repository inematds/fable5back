MODULE 2.2

🎚️ Control the depth + set limits

Not every task deserves maximum reasoning—and no capable agent should get free rein before you say what it can touch. Two practical tips from the Fable 5 work-agent guide: calibrate analysis depth to the task’s actual complexity, and lock in a diagnostic-only mode before letting the agent take real action.

1

🪜 Not every task calls for maximum effort

🧠 Think of it this way: depth of analysis it's not a "turbo mode" you always turn on to guarantee quality. It's a control you calibrate to the task's actual complexity — using the maximum for something simple wastes time and tokens with no benefit; using the minimum for a costly decision is the other, equally common mistake.

The practical guide to using Fable 5 as a work agent sums this up in a four-step scale. Each step isn’t a technical setting — it’s an instruction you write in the prompt yourself, telling the agent how much it’s worth deliberating before giving you the answer.

The scale works best when you ask yourself before writing the prompt: "if this answer comes out wrong, what do I lose?" The more you stand to lose, the higher the level you should ask for.

Level When to use Examples from the guide
Low Mechanical task, low risk of error Summary, caption, text adjustment, quick ideas
Medium Organize or compare options Simple planning, comparison, content review
High A decision that would be costly if it goes wrong Strategy, architecture, auditing, product decisions, technical review
Maximum Costly or irreversible error Critical problems, migration, security, complex business issues, risk analysis

Source: practical user guide to using Fable 5 as a work agent — prompt tested in practice, not an official Anthropic quote.

The 4-level ladder: each step increases reasoning time (dashed cyan line)— máxima stands out because it’s the level you should reserve for when a mistake really costs a lot.

In one sentence: 4 depth levels (low→maximum) calibrated by the question “if it goes wrong, what do I lose?” — not by the habit of always asking for the maximum.

2

💻 The prompt: tailor-made depth

Instead of trusting the agent to guess the right level on its own, you explicitly say where to focus the heavy reasoning — and where it isn’t worthwhile. This avoids the most common symptom of leaving everything at “high all the time”: solutions that are more complicated than the task calls for.

The prompt below does exactly that: it separates the part that deserves depth (the strategic decision) from the part that doesn’t (the implementation itself, which should stay simple).

Goal: avoid overengineered solutions by asking for deep reasoning only where it really matters.
prompt: calibrated depth
Use análise profunda apenas na parte estratégica. Não complique a
solução. Não crie abstrações desnecessárias. Entregue a solução mais
simples que resolve bem o problema.

<isto você troca — cole junto o pedido real da tarefa>
How to check: run the same request twice — once with this instruction, once without it. The version with the instruction should be more direct, with fewer layers/abstractions you didn’t ask for, while still getting the strategic decision behind the request right.

3

⚠️ Too much initiative is risky

A strong model isn't cautious by default — it is capable by default. This means that when a request is ambiguous, Fable 5 tends to fill in the gap on its own: if you asked it to “solve the problem,” it may decide for itself what counts as solving it, and take action.

This is great when you want it to continue until a clearly defined task is done. It's dangerous when the task is ambiguous about what it can touch — files, services, configuration, production data.

⚠️ Common scenario

You ask: "analyze and fix the service's performance problem". Without an explicit boundary, a capable agent may interpret "solve it" as permission to restart the production service, change configuration, or deploy—all without asking you first, because it technically did what you asked.

✓ What to DO

  • ✓Explicitly say what it no can proceed before asking for analysis or execution.
  • ✓Separate the diagnosis phase from the action phase in sensitive tasks.
  • ✓Treating "fix this" as an incomplete request until you define the boundaries.

✗ What to AVOID

  • ✗Ask “fix this” or “take care of this” without saying what is off-limits.
  • ✗Assuming the agent will ask before acting—in general, it acts.
  • ✗Confusing “strong model” with “cautious model”—they’re different things.

In one sentence: the more capable the model, the more explicit the boundary needs to be before asking for technical analysis or execution.

4

🚧 The prompt: evaluate first, execute afterward

The most reliable way to enforce the boundary from the previous topic is to put the agent in a diagnostics-only mode explicit: it can inspect, measure, and draw conclusions — but it can't change anything until you approve.

Goal: lock the agent into evaluation mode before taking any real action in the system.
prompt: safe analysis
Primeiro apenas avalie. Não altere arquivos, não reinicie serviços,
não crie branch, não edite configuração e não rode comandos
destrutivos.

Entregue um diagnóstico com evidências. Depois diga exatamente quais
mudanças recomenda e por quê.

<isto você troca — descreva o sistema ou problema a investigar>
How to check: check that no files were changed, no services restarted, and no destructive commands ran—and that the response ends with a diagnosis + separate recommendations, still awaiting your approval in a later round.

The gate separates the two paths: diagnostics (cyan) are always allowed; actual execution (red) stays locked until you explicitly approve the recommended changes.

In one sentence: "Evaluate first, execute second" turns too much initiative into useful diagnosis—with no risk of unwanted action.

5

🔗 Combining the two: a locked-down audit

The two tips in this module don’t compete—they work together. The clearest example is a security audit: you want high depth (it's a decision that's costly if it goes wrong) e wants the agent locked in diagnostic-only mode (because now isn't the time to change anything yet).

In practice, this becomes a 5-step workflow you repeat for any sensitive task—not just security audits.

1

Define the task and why it needs greater depth

Say what’s at stake — why this task deserves the “high” level and not “medium.”

2

State the boundary: diagnosis only this round

Explicitly list what must not be touched—files, services, configuration, destructive commands.

3

Run it and get the diagnosis with evidence

The agent investigates deeply and delivers verifiable findings, ranked by risk or impact.

4

Review the recommendations

You decide what makes sense to apply—the agent has already said exactly what and why.

5

Approve the changes in a separate round

Only now does the agent execute — and only what you approved, not what it thinks is best.

Goal: asking for a high-depth security audit, but locked in diagnosis-only mode—the combined example from both tips.
prompt: locked audit
Perform a complete security audit of <replace this — the system/project>. Use deep analysis — getting this wrong would be costly.

But for this round, only assess: don’t change files, restart services, edit configuration, or run destructive commands.

Deliver a diagnosis with evidence, ranked by risk. Then say exactly what changes you recommend and why — I’ll approve each one before you act.
How to check: the response must present findings with real evidence (file, line, log, or output—not a generic claim), ranked by risk, and make no actual changes to the system. If anything was changed without your approval, the prompt failed to enforce the limit.

In one sentence: high depth decides how deep the agent thinks; the diagnostic-only mode decides what it can do with what it thought through—the two together provide the safest audit.

6

✅ Common mistakes + quick checklist

Before closing the module, here’s a quick checklist to review the prompts you just learned—calibrated depth (Tip 3) and explicit limits before acting (Tip 4).

✓ Checklist before sending the prompt

  • ✓I asked “if it goes wrong, what do I lose?” before choosing the level of depth.
  • ✓Explicitly said what the agent no can proceed, not just what it should do.
  • ✓I separated diagnosis from execution for any task that touches production or real data.
  • ✓I asked for real evidence in the diagnosis—not a generic opinion.

✗ Most common mistakes

  • ✗Leaving everything at maximum depth “just to be safe,” without measuring whether the time and cost are worth it.
  • ✗Ask “fix this” without saying what’s off-limits—and be surprised by what the agent touched.
  • ✗Mixing diagnosis and execution in the same request for a sensitive task.
  • ✗Accept "done" without evidence—that's the subject of the next module, but it's worth preventing here.

💡 Practical tip: save both prompts from this module (calibrated depth + safe analysis) in a template file. You’ll reuse them whenever you ask for something strategic or something that affects a system—and you’ll quickly notice that many of the “surprises” with powerful agents disappear once these two habits become standard.

In one sentence: calibrate the effort, state the limit — the two habits that prevent most surprises with a capable agent.
